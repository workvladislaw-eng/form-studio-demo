# Правила роботи над SVG → 3D

Цей файл застосовується до всього репозиторію. Мова пояснень і документації — українська; ідентифікатори коду й API — англійська. Прямі інструкції користувача мають пріоритет. Рутинні оборотні зміни в межах задачі виконуй без повторного запиту дозволу.

## 1. Стан проєкту та порядок читання

На момент створення тут лише архітектура й специфікації; код, package manager, середовище та тестові команди ще не налаштовані. Не заявляй, що застосунок або тести працюють, поки це не перевірено.

Перед реалізацією прочитай ARCHITECTURE.md і релевантні специфікації:

- MVP_SPEC.md визначає обсяг і поведінку продукту.
- SCENE_SPEC.md визначає контракт сцени.
- RENDER_SPEC.md визначає трактування сцени й якість рендера.
- API_SPEC.md визначає транспорт, стани та доступ.

Детальна специфікація має пріоритет над альтернативами в загальному огляді. Суперечності між детальними документами виправляй разом із реалізацією; не обирай приховане трактування. Рішення, залежне від вимірювань, позначай як неперевірене.

## 2. Запропоновані межі коду

```text
apps/web/                 редактор, UI, локальний стан
apps/api/                 HTTP, доступ, збереження, постановка задач
workers/geometry/         SVG → перевірений mesh
workers/render/           Python, Blender adapter, encoding
packages/contracts/       JSON Schema, OpenAPI, згенеровані типи
packages/scene-core/      чисті операції над сценою
packages/geometry-core/   нормалізація, топологія, геометрія
packages/renderer-web/    Three.js adapter
tests/fixtures/           SVG, сцени, ресурсні manifests
tests/integration/        контракти, черги, доступ
docs/decisions/           короткі рішення з причиною й наслідками
```

Це цільова структура, не вимога створювати порожні каталоги. UI не імпортує Python/Blender або DB. Scene-core і contracts не залежать від Three.js чи Blender. API не виконує GPU-рендер у процесі HTTP. Worker не приймає довільних команд чи шляхів від користувача.

## 3. Незмінні принципи

- Єдине джерело істини — версіонований scene JSON; одна геометрія для браузера та Cycles.
- Дані на зовнішніх межах проходять runtime-валідацію. TypeScript type сам по собі не перевіряє JSON.
- Ревізії, manifests і ресурси для рендера незмінні. Версія бібліотечного стилю не змінює старі проєкти.
- Координати, scale, alpha й колір конвертуються явно; жодних прихованих magic constants для виправлення вигляду.
- Непідтримувані SVG відхиляються зрозуміло. Не маскуй збої geometry fallback-об’єктом.
- Resource ownership перевіряється на сервері, включно з вкладеними references та cache hits.
- Помилки мають стабільний code; логи мають requestId/jobId, без секретів, signed URLs та повних SVG користувача.

## 4. Зміни контрактів і залежностей

До інтеграції реалізуй JSON Schema та OpenAPI в packages/contracts і згенеруй/перевір типи TS/Python. Не підтримуй незалежні ручні копії моделі сцени. При зміні полів одночасно онови специфікацію, schema, adapters і fixtures. Breaking change потребує нової schemaVersion і явної міграції; старі snapshots не переписуються на місці.

Фіксуй версії залежностей lockfile, Blender і renderer build. Нову залежність додавай за конкретної потреби, перевіряй ліцензію та сумісність; пояснюй вибір у результаті роботи. Не встановлюй інструменти глобально, коли достатньо локального середовища.

Рішення про renderer, color pipeline, геометричний kernel, зберігання та auth оформлюй коротким docs/decisions/NNNN-name.md: проблема, вибір, альтернативи, наслідки, статус перевірки. Не створюй ADR для дрібного UI-виправлення.

## 5. Перевірки

Для документації достатньо перевірки узгодженості, посилань та валідності прикладів. Для змін коду запускай релевантні lint/typecheck/unit/integration перевірки, доступні в проєкті. Не вигадуй команди до налаштування toolchain.

Геометрія потребує fixtures з отворами, тонкими деталями та помилками; сцена — schema і serialization round trip; API — ownership, concurrency та state transitions; renderer — збережених артефактів і візуального огляду. Тест має перевіряти поведінку або інваріант, а не повторювати реалізацію. Не оновлюй еталонні зображення автоматично лише для проходження тесту.

GPU-тести запускай, коли зміна впливає на рендер і середовище доступне. Якщо GPU/Blender відсутні, виконай незалежні перевірки та явно зазнач неперевірену частину. Не оголошуй renderer готовим за одним mock-тестом.

## 6. Definition of done

Зміна завершена, коли реалізовано узгоджений обсяг; не порушено контракти; виконано релевантні перевірки; оновлено документацію при зміні поведінки; зазначено обмеження й неперевірені припущення. У підсумку коротко поясни що змінилося, як перевірено й що залишається відкритим.

Не розширюй задачу до анімації, платежів або спільного редагування без відповідної потреби. Не видаляй і не перезаписуй сторонні зміни. Перед командами перевір робочу директорію; для шляхів Windows використовуй безпечні literal path операції.
